# Tool Registry and Execution Pipeline

With `dsh-tools`, tool plugins register schemas and executors, and every model tool call runs through a guarded pipeline — allow/deny/ask policy, monotonic guards, around-dispatch wrappers, result inspection, definition-owned content finalization, and a final observe-only notification. The package also controls how tools are presented to the model: its `mode` config selects native function calling, PTC mode, catalog mode, or both, and one agent shadows that default for itself with `presentAs`. `ctx.tools` is the registry every tool plugin registers into and the loop dispatches through; registering a tool is enough to make it visible — the registry feeds its schemas into the system-prompt assembly automatically.

## The execution pipeline

The `tools/pre-execute` waterfall runs first, monotonic guards run next, and the `tools/execute` and `tools/post-execute` waterfalls follow; the three waterfalls may transform a call. Definition-owned `finalizeContent` and `tools/result` run afterward.

1. **`tools/pre-execute`** — hooks, permission, sandbox. An ask routes through `ctx.approval`: `allowed-once` proceeds to the guards, anything else (`rejected`, `cancelled`, `unavailable`) denies and the tool body is skipped.
2. **Monotonic guards** — registered guards deny or abstain; owner policy that must not be reordered stays a guard.
3. **`tools/execute`** — the around-dispatch waterfall (timeout, retry, metrics) wraps the registered tool `execute()` body. Tool-owned session events (`todo/write`, `fs/observed`, `hook/invoked`, `hook/result`, `tool/code-dispatch`) are emitted by the body, and filesystem read-before-edit checks stay below `tool-fs` on `fs/*` events.
4. **`tools/post-execute`** — accept, block, replace, or add context.
5. **Normalization** — the registry losslessly snapshots the candidate result and normalizes a snapshot failure before the visible definition's snapshotted `finalizeContent` callback enforces its synchronous content-only invariant.
6. **`tools/result`** — a synchronous notification observing the frozen authoritative outcome; the active batch's `additionalContexts` FIFO injects a user message after recorded tool results.

PTC mode sends both the reserved `run_code` transport and its serialized sub-calls through the same pipeline; sub-calls carry the parent token, log `tool/code-dispatch`, and return denials as binding rejections.

## `ToolDefinition` and `defineTool`

A `ToolDefinition` is a `ToolSchema` (the model-facing fields) plus a mandatory canonical output declaration, the `execute` function, host-only scheduler metadata, an optional final-content callback, and optional UI presenters. The registry's `schemas()` builds the model-facing `ToolSchema[]` by an explicit allowlist — `output`/`execute`/`finalizeContent`/`timeoutMs`/`isConcurrencySafe`/`device`/`presentCall`/`presentResult` never leak into a model request.

The `output` declaration carries a raw supported JSON Schema enforced against every successful canonical value (`additionalProperties: false` + `required` at runtime, so a mismatched result is rejected as an invalid tool output rather than silently cast), a pure `render(args, value)` projection from validated arguments and value to native/model content, and an optional `presentationMeta` projection computed only for top-level calls. `defineTool` builds this typed definition: model arguments are validated before execution, and invalid input becomes a normal error result. Mounting a tool under `mode: 'catalog'` withholds its full schema from the prompt and makes it reachable only through the reserved `dyn` transport at zero schema slots.

## Catalog generation

`docs/tool-catalog.md` is generated by `scripts/gen-tool-catalog.ts` from schemas collected by **booting each tool plugin**: runtime registration is the source of truth for computed schemas, the manifest is checked against every on-disk `tool-*` package, and `--check` verifies the committed artifact (a freshness gate).

## Result spill policy

The `spill/` group keeps oversized tool output out of the model's context without losing it: when a tool result exceeds a deployment's byte cap, the full text is saved to a spill artifact and the model sees a bounded preview plus a locator it can read or search later. The family splits into the storage service (`spill/`), the local filesystem backend (`spill-local/`), and the result policy (`spill-policy/`) that decides when a final tool result is too large. Spilling is opt-in and best-effort: the policy acts only when `maxInlineBytes` is configured, and a storage failure leaves the original result visible.
