# Agent Note: Node runner cells observe EOF stdin, not the control channel

Status: proposed

English | [中文](2026-10-12-node-runner-stdin-ownership.zh.md)

## Problem

The persistent JS kernel evaluates cells in the runner process itself: `handleExec` runs cell code through `new Function` in the same process whose wire loop reads control frames on `process.stdin` (`packages/code-runtime/code-runtime-kernels/src/nodejs/runner.ts:473`). `process.stdin` is the lazy Node getter wrapping fd 0, so the wire loop and any cell share one stream. A cell that touches `process.stdin` — attaching a `'data'` listener, calling `read()`, `pipe()`-ing it, or resuming it — races the control reader: it can consume NDJSON control frames (the kernel wedges waiting for a reply a cell swallowed), pause the shared stream so the wire loop starves, or interleave competing listeners. The failure is silent: nothing distinguishes stolen frames from a lost protocol.

The Python runner already owns a documented contract for this exact surface: `src/python/runner.ts:70-84` dups fd 0 to a private `_CONTROL_IN` and repoints fd 0 at the null device, so user code reads immediate EOF instead of blocking on (or stealing frames from) the control channel. The JS runner has no equivalent: its only stdin protection is the host-side `'error'` listener added when the host crashed writing to a dead child (`src/core/kernel.ts:388`), which does nothing about in-process contention.

Two constraints shape the fix. First, there is no upstream fix to harvest: upstream evaluates JS cells in worker threads, which have no stdin at all, while the fork's persistent-kernel design — program-created globals and snapshot restoration in the runner's global scope — requires the runner process itself. Second, **the runner process alone cannot duplicate a pipe descriptor**: Node exposes no `dup`/`dup2` (`typeof fs.dup === 'undefined'`), `fs.createReadStream(null, { fd: 0 })` takes ownership of the descriptor *number*, not a duplicate — after `closeSync(0)` the private stream reads the wrong thing or dies (EBADF, then the host's next frame write fails EPIPE), leaving the kernel exactly the silent wedge this fix exists to prevent — and `/dev/fd/0`-style reopenings are POSIX-only. An in-runner fd dance is therefore not a portable mechanism; the decision must move to the spawn boundary, where the host controls what fd 0 *is*.

## Proposal

**Decision: the control channel is a first-class wire, not stdin. The host spawns the JS runner with fd 0 = `'ignore'` and passes control frames on a dedicated fd 3 pipe; the runner adopts fd 3 for its wire loop. Cells then observe immediate-EOF `process.stdin` natively, with no fd manipulation in the runner at all — the observable contract of the Python runner, reached by a Node-appropriate mechanism.**

The decision is the *contract* — "fd 0 carries no control traffic; cells see EOF stdin" — while each runtime chooses its mechanism: Python keeps its working `_CONTROL_IN` dup, JS gets fd 3.

1. **Host (`src/core/kernel.ts:323`)**: `KernelRuntimeProfile` gains a control-fd declaration (e.g. `controlFd?: number`). For the JS profile the spawn options become `stdio: ['ignore', 'pipe', 'pipe', 'pipe']` and the outbound frame writer targets `proc.stdio[3]` instead of `proc.stdin`. Profiles without a declaration spawn and write exactly as today, so the Python runner is untouched.
2. **Runner (`nodejs/runner.ts:473`)**: the boot ladder keys on host-authenticated intent, then on descriptor type — never on `isFIFO()`, which is false for libuv spawn pipes on POSIX (they are AF_UNIX socketpairs, `S_IFSOCK`) and hardcoded false on Windows even when `st.mode` carries `S_IFIFO` (nodejs/node#57603). Pipe-like means `(st.mode & fs.constants.S_IFIFO) !== 0 || st.isSocket()`.
   - **Marker present** (`DSH_KERNEL_CONTROL_FD=3`, set by the new host in the profile env it already merges at spawn — `src/core/kernel.ts:325`): probe fd 3. **Pipe-like → adopt** — `new net.Socket({ fd: 3, readable: true, writable: false })` — and attach the existing `FrameLineSplitter` wire loop to that stream (the no-trailing-flush-at-end contract at `nodejs/runner.ts:415-423` carries over unchanged). The libuv stream wrapper is load-bearing, not a stylistic choice: spawn-pipe fds are blocking in the child, so `fs.createReadStream(null, { fd: 3 })` pins one of the four threadpool workers in a blocked read for the kernel's entire lifetime — starving every other fs-threadpool consumer the process will ever run; a `net.Socket` opens the fd through libuv (non-blocking), delivers frames, and exits cleanly. **Not pipe-like → fail loudly**: the marker says the host intended fd 3 but a confinement wrapper ate it — emit a `control-fd-missing` protocol frame on the stdout emit wire (which still works) naming the missing control fd, flush it synchronously (`fs.writeSync(1, line)` via the raw fd — `emit`'s `rawStdout.write` is fire-and-forget and `process.exit()` truncates pending async stdout writes on macOS), then exit non-zero. The host gains a dispatch arm for that frame — `parseKernelFrame`'s default arm drops unknown types (`src/core/kernel.ts:261`), the run-scoped `'error'` frame is dropped at boot with no active run, and boot-time stderr is ingested as stray — so `#handleFrame` must fail start fast with the named diagnosis; otherwise the operator sees only the generic "exited before becoming ready" and the silent-failure problem recurs one level up. Never fall back to a null-device wire; a silent EOF loop is the dead-kernel wedge this decision exists to prevent.
   - **Marker absent** (old host, manual TTY run): wire the loop on `process.stdin`, today's behavior. The marker is what makes this rung safe — a foreign descriptor inherited at fd 3 (the harness's own bash-tool environment passes one) is never adopted, because descriptor type alone cannot authenticate intent.
   The `'ready'` handshake is emitted only after a rung is taken, so the host never writes into an unowned pipe.
3. **Confinement passes the control fd through.** The wired confinement path inserts a wrapper between host and runner (`config.confine(fullArgv).argv` at `src/core/kernel.ts:322`; the Linux rung is bwrap at `packages/sandbox/sandbox-local/src/index.ts:349`). Bubblewrap has no fd-stripping option and no `--preserve-fd`: it passes inherited fds above 2 through to the sandboxed command — the sandboxed child's exec path never closes extra fds (upstream source: "Any other fds will been passed on to the child though") — so the fd-3 pipe already survives the existing profile unchanged; the only requirement is that the host spawns the wrapper with the 4-entry stdio it already controls at `src/core/kernel.ts:323`. Wrappers that genuinely close inherited fds are unsupported for the JS control wire, and their breakage surfaces through the loud-failure rung above; the real-bwrap e2e (`packages/sandbox/sandbox-local/tests/bwrap.e2e.ts`) pins that the runner observes a pipe-like fd 3 under the current profile.
4. **What cells see**: fd 0 is the `'ignore'` stdio (the null device on every platform). The first cell that touches `process.stdin` lazily constructs the getter's Readable on it: reads return immediate EOF, and `isTTY` is unset (not a TTY — assert falsy, not `=== false`). The runner never touches `process.stdin` in the fd-3 path, so there is no boot-ordering invariant to maintain.
5. **Children**: a cell spawning a child with explicit `stdio: 'inherit'` passes the null device as stdin (immediate EOF). A child spawned with Node's *default* `stdio: 'pipe'` gets a fresh pipe, not fd 0 — that is ordinary Node semantics and a deliberate divergence from Python, where `stdin=None` inherits fd 0; the note records the divergence rather than fighting it.

Out of scope: the stdout side (`emit` owns the wire; direct `process.stdout.write` is intentionally unpatched per the `installOutputCapture` comment), `process.exit()`/SIGINT semantics, and any interactive-input feature for cells (a real cell stdin would be a host-mediated binding, not fd 0).

## Alternatives considered

**In-runner fd dance (first draft of this proposal): adopt fd 0 with `fs.createReadStream(null, { fd: 0 })`, then `closeSync(0)` + reopen the null device.** Rejected on evidence: the stream owns the descriptor number, not a duplicate — the close tears the control pipe down (stream EBADF, host EPIPE), or if the reopen lands first, the stream reads the null device and the wire loop goes permanently deaf. Also carried a Python-ism spelling (`os.devnull` — Node spells it `os.devNull`, and neither is needed under this decision) and an unreachable TTY fallback after `closeSync(0)`. Recorded here because the failure mode — silent kernel death — is precisely what the contract forbids.

**POSIX-only duplicate via `/dev/fd/0` / `/proc/self/fd/0` reopen.** Rejected as non-portable: the kernels suite must stay Windows-portable, and Windows has no equivalent reopen of an inherited pipe.

**Replace the `process.stdin` getter with a stub** (error-throwing, or an EOF `PassThrough`). Rejected: an error is not EOF (diverges from the Python contract), it lies about `isTTY`, and it fights the lazy getter's caching — while still leaving the control channel on a shared descriptor.

**Evaluate cells in worker threads (upstream's model).** Rejected for this gap: workers have no stdin, so the hazard vanishes structurally, but the persistence model is the thing being rewritten — `state`, program-created globals, and snapshot restoration all live in the runner's global scope. That is a different kernel design, not a fix.

**Document "cells must not touch `process.stdin`" and change nothing.** Rejected: the failure mode is a silently wedged kernel with no diagnostic; a contract that only exists in prose cannot protect the wire.

## Acceptance criteria

- A cell that reads `process.stdin` observes immediate EOF (an `'end'` with no `'data'`), and the wire loop still delivers a subsequent `exec` frame afterward — pinned by a regression test in the kernels suite that spawns the new stdio and exercises adoption, not just the fallback, on both POSIX and Windows.
- A child spawned by a cell with explicit `stdio: 'inherit'` reads immediate EOF on stdin; a default-`'pipe'` child gets a fresh pipe (documented Node divergence).
- `process.stdin.isTTY` is unset in the fd-3 mode; the kernels suite stays green (86-test baseline) including its Windows-portable gates.
- Marker absent (old-host/TTY): the wire loop behaves exactly as today, and an inherited foreign descriptor at fd 3 is ignored. Marker present but fd 3 not pipe-like (a wrapper that strips fds): the runner emits a loud protocol error and exits non-zero rather than wedging, and `sandboxConfinement` + JS kernels passes its suite with the runner observing a pipe-like fd 3 under the current bwrap profile (real-bwrap e2e).

## Risks

- **The contract ships as a host+runner pair, with confinement as a third party.** The spawn options (including the `DSH_KERNEL_CONTROL_FD` marker), the outbound writer target, the runner's boot ladder, and the `control-fd-missing` frame's host dispatch arm must land together; the ladder's loud-failure rung keeps a mismatched trio failing visibly rather than wedging silently. Confinement needs no extra flags — bwrap passes inherited fds through — but any wrapper that strips fds is unsupported for the JS control wire and surfaces via that rung.
- **Descriptor type alone cannot authenticate the wire**: pipe-like is `(st.mode & S_IFIFO) !== 0 || st.isSocket()` — never `isFIFO()`, which misses libuv socketpairs on POSIX and lies on Windows (nodejs/node#57603) — and the env marker is what separates "host intent" from "inherited coincidence".
- **Host write-backpressure** moves from `proc.stdin` to `proc.stdio[3]`; the serialized outbound writer must handle the new stream's `'error'`/`'drain'` exactly as it does today.
- The 86-test baseline and Windows gates must stay green; the fd-3 probe path needs a test spawned with the new stdio to exercise adoption, not just the fallback.
